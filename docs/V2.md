# v2.0.0 — opt-in registration for dedicated tenants

For the person who approved this work. Tag **`v2.0.0`** (`9b72cd4`), baseline **`v1.0.0`**
(`a1626d0`). Nothing has been pushed; the tag and every commit are local.

The brief was [`docs/PLAN-opt-in-registration.md`](./PLAN-opt-in-registration.md), which now
carries a status line per phase. This file is the answer to five questions: what changed, what a
dedicated tenant costs now, how to run the whole thing, what is broken, and what you should argue
with.

**Read §4 before you demo this to anybody.** One of the findings makes the demo destroy a
merchant's orders if you recover from it the documented way.

---

## 1. What changed

Five commits of substance, in the order they happened. Each one has a diary entry under `diary/`
and a lessons file under `lessons/` with the same number.

| | Commit | |
|---|---|---|
| **Phase 0** | `1c6f609` | The dedicated instance runs on **real OIDC**, not the stub. Two things were broken and both were small: `IDENTITY_CACHE_PATH_DEDICATED` was never set by AppHost A, so the file the adapter reads in its constructor did not exist; and A registered `127.0.0.1:…/auth/callback` while B asked for `localhost:…/auth/callback`, which Logto compares as strings |
| **Phase 1** | `93fd588` | **Opt-in, host-pinned registration.** The instance presents its one-time bootstrap token, says where it lives, and the control plane registers exactly that with the issuer and hands back `{issuer, clientId, clientSecret}` for a client minted for that installation alone (`CE1`). `DELETE /installations/:id` was built at the same time (`CK1`) and takes the client and its redirect URIs away again. `MERCATUS_STORE_DEDICATED_PORT` and `STORE_DEDICATED_URL` are **deleted** — four fixed ports became three |
| **Phase 2** | `106a39b` | **One AppHost B, any tenant**, by `MERCATUS_TENANT_SLUG`. Every resource name, container, database, path and manifest file derives from the slug |
| **Phase 3** | `f7f3d0f` | **A second dedicated tenant**, `orion`, with zero edits to AppHost A. Two blockers were real: a tenant bought after A started had no Logto organization (`ensureOrganizationBySlug`, created from the platform at run time, *not* by teaching A the slug list), and the Aspire CLI treats a running AppHost as a singleton keyed on its file path, so two Bs need two directories |
| **Repair 1** | `e06df86`, `bebcf46`, `8350fdb`, `3661b61` | The first acceptance run failed v2.0.0. The blocker was not a bug in anything that ran: `MERCATUS_AUTH_ADAPTER=oidc` put the store API on a real issuer and left **both browser front ends unable to sign anybody in, on both planes**, because they called `/dev/login/*` directly and those routes exist only under the stub. The store is now the only OIDC client in the topology and both front ends go through its own `/auth/*`; each dedicated box publishes `<slug>.localtest.me:<port>`, so four storefronts stop sharing one cookie jar; `packages/e2e/tests/05-oidc-four-tenants.spec.ts` drives the four-tenant demo against Logto in a real browser |

The one-sentence version: **A mints a token, the instance opts in and tells A where it lives**,
and A no longer has to know a dedicated store's address before that store exists.

Versioning follows the repo policy — a release with features in it bumps the first number, so
`1.0.0 → 2.0.0`, in the root and all 14 workspace packages.

## 2. What a dedicated tenant costs now

### At v1.0.0 — a copied AppHost and ~14 edits in 4 files

Adding `orion` meant copying `aspire/AppHostB/` and changing, **inside the copy**
(`git show v1.0.0:aspire/AppHostB/apphost.cs`):

| Line | |
|---|---|
| 85, 86 | `AuthStubSecret`, `SessionSecret` |
| 92 | `BootstrapToken` |
| 94, 95 | `TenantSlug`, `TenantName` |
| 102 | `storePort` — **a new fixed port, agreed in advance with AppHost A** |
| 109 | `.instance/zenith.json` |
| 121, 122 | `pg-tenant-zenith`, `db-tenant-zenith` |
| 132, 147 | `task-migrate-tenant-zenith`, `task-provision-tenant-zenith` |
| 173 | `api-store-tenant-zenith` |
| 186 | `.identity/store-zenith.json` |
| 220, 229 | `web-storefront-tenant-zenith`, `.next-zenith` |
| 237 | `web-dashboard-tenant-zenith` |
| 249 | `.stack/apphost-b.json` |

Seventeen slug-bearing literals, plus the three CLI ports in `apphost.run.json`. Then three more
files outside it:

- `aspire/AppHostA/apphost.cs` — a second fixed port and a second `STORE_DEDICATED_URL`. This one
  is not an edit so much as a redesign: the variable was singular, so a second dedicated tenant
  meant making A's model hold a *list* of boxes it does not own.
- `packages/identity/src/bootstrap.ts` — `IDENTITY_TENANT_SLUGS`, plus a second `store-dedicated`
  application with its own redirect URIs, registered before that store existed.
- `packages/db-platform/src/seed-dedicated.ts` — the tenant and its bootstrap token.
- `packages/e2e/tests/helpers/*` — the fixed manifest keys `store_dedicated`,
  `storefront_dedicated`, `dashboard_dedicated`, of which there could only ever be one set.

### At v2.0.0 — one command

```bash
aspire/scripts/run-dedicated.sh orion
```

That is the whole of it for a slug the control plane already knows, and **zero edits to AppHost A
in every case**. For any other slug it is four authenticated calls first, which is the path a real
customer takes:

```bash
PLATFORM=http://platform.localtest.me:28080
TOKEN=$(curl -sX POST $PLATFORM/dev/login/operator -H 'content-type: application/json' \
        -d '{"subject":"ops"}' | jq -r .accessToken)              # accessToken, NOT token
curl -sX POST $PLATFORM/tenants -H "authorization: Bearer $TOKEN" \
     -H 'content-type: application/json' \
     -d '{"slug":"vega","name":"Vega Works","tier":"dedicated"}'
curl -sX POST $PLATFORM/tenants/vega/activate -H "authorization: Bearer $TOKEN" \
     -H 'content-type: application/json' -d '{}'
BOOTSTRAP=$(curl -sX POST $PLATFORM/installations -H "authorization: Bearer $TOKEN" \
     -H 'content-type: application/json' \
     -d '{"tenantSlug":"vega","expectedHost":"vega.localtest.me"}' | jq -r .bootstrapToken)

aspire/scripts/run-dedicated.sh vega "$BOOTSTRAP"
```

The acceptance reviewer did exactly this against a live stack and got a third dedicated box.

**The residual costs, stated rather than implied:**

- `zenith` and `orion` are **seeded** into the control plane's database
  (`packages/db-platform/src/seed-dedicated.ts`), which is why they need no token. That is a
  property of the dev loop, not of the product, and it exists because `aspire stop` on A destroys
  A's Postgres. A third slug that should also survive a control-plane rebuild without curls is one
  entry in that file.
- `aspire/scripts/run-dedicated.sh` generates `aspire/AppHostB-<slug>/` — gitignored, rewritten
  every run, a build artifact. It exists because the Aspire CLI stops a running AppHost when
  another `aspire run` names the same apphost **file path**; `--isolated` does not help, and a
  symlink or a byte-identical copy does not either (see `lessons/17`).

## 3. Running two pooled and two dedicated tenants

Two pooled tenants (`acme`, `borg`) come with AppHost A; the two dedicated boxes are one command
each. **`aspire run` must be `--detach`** or the command never returns.

```bash
cd ~/Desktop/projects/mercatus
pnpm install                                      # ~3 s warm

# A -- control plane, identity (Logto), fake-bank, the POOLED store serving acme and borg,
#      the storefront, the merchant dashboard, the platform console, Traefik on 28080.
( cd aspire/AppHostA && aspire run --detach --non-interactive --nologo --format Json )

# Wait for A. Logto takes the longest; B cannot register before the control plane answers.
until curl -fsS -m 4 http://platform.localtest.me:28080/health >/dev/null; do sleep 1; done
until [ -s .identity/management.json ]; do sleep 1; done

# B, twice -- two customer-owned boxes, each with its own Postgres, store process and hostname.
aspire/scripts/run-dedicated.sh zenith
aspire/scripts/run-dedicated.sh orion
```

A is ready in ~15 s, each B in ~10 s more. Where everything landed is written down, because
almost every port is Aspire-assigned:

```bash
cat .stack/apphost-a.json        # platform, store_pooled, bank, storefront, dashboard, admin, edge
cat .stack/apphost-zenith.json   # store, storefront, dashboard -- and the tenant they serve
cat .stack/apphost-orion.json
```

A's surfaces are all on the edge, port **28080**: `shop.localtest.me/t/acme`, `/t/borg`,
`dash.localtest.me`, `console.localtest.me`, `platform.localtest.me`, `bank.localtest.me`. A
dedicated box answers on a hostname of its own, `<slug>.localtest.me:<assigned port>`.

**On a real issuer instead of the stub** — note the `export`, because `VAR=x ( … )` is a bash
syntax error and `docs/MORNING.md` §1 got that wrong:

```bash
export MERCATUS_AUTH_ADAPTER=oidc
( cd aspire/AppHostA && aspire run --detach --non-interactive --nologo --format Json )
aspire/scripts/run-dedicated.sh zenith
aspire/scripts/run-dedicated.sh orion
```

**The checks**, and what each one really covers:

```bash
pnpm -r test                     # 261 passed, 0 skipped, ~35 s. No stack. No browser at all (FO)
pnpm turbo run typecheck lint    # 26/26
pnpm test:e2e                    # on a STUB stack: 22 passed, 6 skipped, ~1.6 min
MERCATUS_E2E_REQUIRE_OIDC=1 pnpm test:e2e     # on an OIDC stack: 6 passed, 22 skipped, ~51 s
```

Those last two are **two runs of the same command against two configurations**, not the same
tests twice. See **FK**.

**Down, dedicated boxes first so their credentials stay valid:**

```bash
aspire/scripts/stop-dedicated.sh orion
aspire/scripts/stop-dedicated.sh zenith
( cd aspire/AppHostA && aspire stop --non-interactive --nologo )
docker ps                        # nothing of ours should remain
pgrep -af 'aspire-managed nuget' # FQ: kill any of these by pid; aspire stop leaves them
rm -f .stack/apphost-*.json      # FN: these are NOT removed by aspire stop and go stale
```

## 4. What does not work

Nine findings from the acceptance run, given stable labels here (**FJ**–**FR**) so they can be
pointed at. Severity order is the reviewer's. Everything below was reproduced against a live
stack by the reviewer; where I checked something myself in this handover I say so.

### FJ — a control-plane rebuild breaks sign-in at every running dedicated box, and the fix destroys the merchant's data

The worst thing in the release, and it is the demo's own recovery path.

With `zenith` and `orion` still up and selling, `aspire stop && aspire run` on AppHost A leaves:

- `GET /installations` at `total: 0` — the platform console reads "Registered instances 0" while
  two boxes are serving;
- `GET /auth/login` on the dedicated store, which 302s to the issuer, answering **HTTP 400
  `oidc.invalid_client`** for the per-installation client that no longer exists. **No new shopper
  and no new staff member can sign in.** Existing cookie sessions keep working, which is exactly
  what hides it;
- no recovery, ever, by design: re-registration runs only in the install command at B's **start**
  (`apps/store/src/provision.ts`).

The documented fix is to restart the box — and that **recreates `pg-tenant-<slug>` from scratch**.
The reviewer measured zenith's order count going **4 → 0** across its restart. Neither AppHost
declares `WithDataVolume` anywhere (I re-checked: `grep -rn WithDataVolume aspire/` finds
nothing), so A's Postgres *and* Logto's Postgres are both ephemeral, which is why the
per-installation OIDC client dies with them.

`docs/OPEN-DEFECTS.md` logs this as **EV** and understates both halves: it says only that "B's
instance token answers 401 for ever" and that "restarting B fixes it in one poll". Sign-in dies
too, and the fix empties the customer's store.

The fix is the same re-register branch in `apps/store/src/agents/licence-poll.ts`, plus a data
volume on both Postgres resources. Neither was done.

### FK — the browser suite cannot prove the definition of done in any single run

Specs `01`–`04` call `stubOnlyReason()` and skip their whole file under `AUTH_ADAPTER=oidc`;
spec `05` skips under the stub. Measured: **stub 22 passed / 6 skipped, oidc 6 passed / 22
skipped.** The plan's definition of done says "real OIDC on both planes", and on that stack the
passive-licence file, the pooled cross-tenant-isolation file, the outage file and the whole
four-tenant file never execute — so the passive-licence, outage, cross-tenant-isolation and
four-tenant claims have automated evidence **only under the stub adapter**.

The mechanical cause is narrow: `licenceView()`, `staffToken()` and `setTenantLicence()` in
`packages/e2e/tests/helpers/stack.ts` all go through `POST /dev/login/staff`, which
`apps/store/src/routes/dev-login.ts` registers only when `AUTH_ADAPTER=stub`.

### FL — the README misrepresented the OIDC run

`README.md` listed `pnpm test:e2e # 22 Playwright tests …` and immediately under it
`MERCATUS_E2E_REQUIRE_OIDC=1 pnpm test:e2e`, which reads as the same 22 tests with the adapter
swapped. It runs 6 and skips 22. **Fixed in this handover**, in the README and here.

### FM — "the platform console shows both installations" has no test

Neither `04-two-dedicated-tenants.spec.ts` nor `05-oidc-four-tenants.spec.ts` ever opens the
console; the only console assertion in the whole suite is spec `02`'s passive-licence badge. The
reviewer verified it by hand (three rows — `zenith`, `orion` and a `vega` created live — with
version, last-seen, product and order counts). Given **FJ** makes that claim false after any
control-plane restart, it is the claim that most needed a test.

### FN — `.stack/*.json` survive `aspire stop` and go stale

Neither `aspire/scripts/stop-dedicated.sh` nor either AppHost removes them. I confirmed this in
this handover: with nothing running (`docker ps` shows only an unrelated container, nothing
listening on 28080/28311/28312/15230/15240), all three of `apphost-a.json`, `apphost-zenith.json`
and `apphost-orion.json` are still on disk naming dead ephemeral ports.

Two consequences. `global-setup.ts`'s fast "No running stack found" branch keys on `url === ''`
and is unreachable after the first run, so a down stack costs a 90-second timeout instead of one
sentence. And an ephemeral port the OS later hands to an unrelated process would be probed as if
it were a store.

### FO — `pnpm -r test` never opens a browser

`packages/e2e` declares `test:e2e` and no `test` script, so the headline command covers 13 of 14
workspace projects and none of the storefront, dashboard, console, edge or outage behaviour.
`apps/storefront`, `apps/dashboard`, `apps/admin`, `packages/ui` and `packages/identity` have no
`test` script at all. This is **EZ** in `docs/OPEN-DEFECTS.md`; it means a green
`pnpm -r test` says nothing whatever about the storefront, the dashboards, the console, the edge
or the outage story.

### FP — documentation errors on the newcomer's path

`README.md` said "the edge on 8080" in the first run command (it is 28080 everywhere else,
including 34 lines below), and claimed "the two dashboards are on 15230 (A) and 15240 (B)" when
the documented way to start B is `run-dedicated.sh`, which always passes `--isolated` and
randomises exactly those ports — observed across four starts as 35345, 35083, 37723, 43177, never
15240. `REQUIREMENTS.md` repeated it. **All fixed in this handover**, along with a bash syntax
error in `docs/MORNING.md` §1 (`MERCATUS_AUTH_ADAPTER=oidc ( cd … )` does not parse).

### FQ — `aspire stop` leaks a process per generated run directory

Two `aspire-managed nuget search --query Aspire.Cli … --working-dir …/aspire/AppHostB-zenith|orion`
processes survived every `aspire stop` and had to be killed by hand. This is the Aspire CLI's
doing rather than this repo's code, but nothing in the teardown path or the docs accounts for it,
so "leave the machine clean" is not reachable with the documented commands alone. The teardown
block in §3 now names it.

### FR — a failed host-pin check does not burn the bootstrap token

Two mismatched `baseUrl`s (including the suffix attack `http://vega.localtest.me.evil.example:9999`)
were correctly refused with the generic 401, and the same token then registered successfully. That
is a deliberate trade — a wrong guess should not brick a legitimate install — but the one-time
semantics are documented in `apps/platform/src/routes/installations.ts` and the README **without
this exception**, and it is the difference between one attempt and unlimited attempts for anyone
holding a leaked token.

### Carried over from v1.0.0, still shipping

Stated in full in [`docs/OPEN-DEFECTS.md`](./OPEN-DEFECTS.md); none of them was touched.

| | |
|---|---|
| **EW** | one port covers HTML and nothing else. Every SPA XHR and the whole payment leg leave the edge at direct addresses. Firewall everything but `:28080` and checkout breaks |
| **EX** | CORS is `origin: true, credentials: true` on every API — which is also what keeps EW invisible |
| **CE2** | the storefront signs fake-bank requests itself, **including on a customer-owned box**. `POST /payments/proxy` was never built |
| **EY** | the merchant cannot see who bought; the order detail renders no shopper |
| **F4, F5, F6** | the control plane has no RLS (informational); a PK collision is an existence oracle; a non-UUID `app.tenant_id` raises at query time |

### How much of this I re-verified

I did not start the stack for this handover. The live numbers in §3 and §4 are the reviewer's and
the repair round's, both measured on this machine. What I checked myself today: the tree is clean
at `v2.0.0`; `MERCATUS_STORE_DEDICATED_PORT` survives only in comments and prose; no
`WithDataVolume` anywhere; `packages/e2e` has no `test` script; `01`–`04` all call
`stubOnlyReason()` and `05` gates on `MERCATUS_E2E_REQUIRE_OIDC`; the helpers do go through
`/dev/login/staff`; the stack is down and `.stack/*.json` are still there; no leaked Aspire
processes are alive right now.

## 5. Decisions you should review

Each of these was a fork in the road, and the diaries argue them at length. These are the ones
where a reasonable person could have gone the other way.

1. **One OIDC application per *installation*, not per tenant.** Measured, not theorised: keyed on
   the slug, a second `zenith` installation put both redirect URIs on one application, and
   `DELETE /installations/:id` on a throwaway would have deleted a live box's client. The cost is
   an application at the issuer per box, for ever, unless deprovisioning is actually called.
2. **The store is the only OIDC client in the topology.** Both front ends sign in through its
   `/auth/*`, and `POST /auth/exchange` hands the store's own session back as a bearer token to a
   front end on another origin. The alternatives — a client per front end, or a `Domain=` cookie
   across `localtest.me` — were rejected because a browser bundle cannot hold a secret and a
   domain cookie would give every instance every other instance's session. **The consequence to
   weigh: a bearer the adapter rejects is retried against the store's `SessionIssuer`**
   (`packages/core/src/auth/plugin.ts`). One credential, two transports.
3. **The platform holds Logto's M2M credential, read from a 0600 handoff file**
   (`IDENTITY_MANAGEMENT_OUT` → `LOGTO_MANAGEMENT_PATH`), opened lazily on first registration and
   never at boot. The bootstrap gets that secret by reading Logto's own Postgres and the platform
   must not, so something had to carry it. A file on disk is the compromise.
4. **`zenith` and `orion` are seeded into the control plane.** It makes the four-tenant demo one
   command per box — and it flatters the demo, because the real path is the four curls. It exists
   only because A's Postgres is ephemeral (**FJ**).
5. **The control plane creates a `<slug>_owner` user at the issuer** for a tenant bought at run
   time, gated on `IDENTITY_DEV_PASSWORD`. In a product a merchant is invited and sets their own
   password; this is a dev affordance sitting in production code paths.
6. **The host pin is on the hostname only, never the port**, and a failed pin does not burn the
   token (**FR**). Both are defensible; both are choices you may want stated differently.
7. **Generated `aspire/AppHostB-<slug>/` directories.** A build artifact produced by a shell
   script, working around a CLI singleton. It is ugly and it is the smallest thing that works.
8. **No guest checkout any more.** `POST /api/checkout` used to accept a phone number and mint a
   session; there is no way to mint one without the issuer now. A phone was never an identity
   (`BI2`), but this is a product change made in a plumbing task.
9. **Two e2e runs rather than one.** `01`–`04` mint a fresh shopper per run, which under a real
   issuer needs a Logto user created per run through the Management API — a credential the suite
   has no business holding. The consequence is **FK**, and the alternative (seeded shoppers with
   delta assertions, as `05` does) was judged a bigger change than the round had room for.

## 6. Was the definition of done met?

The plan's closing line, item by item. **Five of seven are met outright; one is met only on the
stub adapter; one is met with an exception nobody wrote down.**

| | Item | Verdict |
|---|---|---|
| 1 | **Two pooled tenants** | ✅ `acme` and `borg`, one store process, RLS-isolated, with a leak suite that is provably able to fail (`MERCATUS_LEAK_SABOTAGE=products`) |
| 2 | **Two dedicated tenants** | ✅ `zenith` and `orion`, own Postgres, own store process, own hostname each, serving at the same time |
| 3 | **Real OIDC on both planes** | ⚠️ **True of the system, not of the evidence.** Both front ends sign in through the store's `/auth/*` under either adapter, and `05-oidc-four-tenants.spec.ts` drives all four shops and four dashboards against Logto in a real browser. But `01`–`04` skip entirely on that stack, so the licence, outage and isolation claims are proved only on the stub (**FK**) |
| 4 | **One shopper account across all of them** | ✅ Proved twice: under the stub by `04`, and under Logto by `05` — one sign-in, four shops across three origins, the same subject string at every one |
| 5 | **`MERCATUS_STORE_DEDICATED_PORT` gone** | ✅ Deleted. It survives only in comments and docs explaining its removal. Fixed ports went from four to three: `28080`, `28311`, `28312` |
| 6 | **A host-pinned bootstrap token** | ⚠️ Met, and it refuses the obvious attacks including the suffix one — but a failed pin does not burn the token, which the docs do not say (**FR**) |
| 7 | **A new dedicated tenant costs one command and zero edits to AppHost A** | ✅ One command for a seeded slug; four authenticated calls and then one command for any other; zero edits to AppHost A either way, confirmed live by the reviewer creating a third box |

**The phase gates** all executed and all passed: a real browser login on the dedicated store
(phase 0); registration on an Aspire-assigned port with the redirect URI confirmed through the
Management API and a mismatched host refused (phase 1); `MERCATUS_TENANT_SLUG=zenith` reproducing
v1.0.0 behaviour with the suite green (phase 2); four tenants serving at once, one shopper buying
at all four, each merchant seeing only its own orders, and both dedicated stores still completing
checkout with the control plane stopped (phase 3).

**The honest summary.** As a *running system* the plan was delivered. As a *self-proving* system
it was not: no single command demonstrates the definition of done (**FK**, **FO**), the claim that
the console shows both installations is untested and is false after any control-plane restart
(**FM**, **FJ**), and the release's own recovery procedure destroys a merchant's orders (**FJ**).

## 7. What I would fix first

In order, and the first one is not close.

1. **FJ.** Put the re-register branch in `apps/store/src/agents/licence-poll.ts` so a running box
   recovers by itself, and give `pg-platform`, `pg-identity` and `pg-tenant-<slug>` a
   `WithDataVolume` so "restart the control plane" stops meaning "delete a merchant's orders".
2. **FK.** Make `licenceView()`, `staffToken()` and `setTenantLicence()` adapter-agnostic — read
   the token the merchant's browser was handed, as `05` already does — and `01`–`04` stop skipping
   under `oidc`.
3. **FM.** One console assertion in `04`, so `total: 2` is a test and not a screenshot.
4. **FN, FQ.** Remove `.stack/apphost-*.json` on stop; account for the leaked CLI process.
5. **EW + EX** together: point `VITE_STORE_API_URL`, `VITE_PLATFORM_URL` and `FAKE_BANK_URL` at
   the edge hostnames and narrow CORS to them. It is one change and it makes the edge claim true.
